	/* get current thread pointer */

	/* calculate time to wake up */
	current_thread->wakeup_tick = start + ticks;	

	/* disable interrupt to safely modify sleep_list */
	enum intr_level old_level = intr_disable();

	list_insert_ordered(&sleep_list, &current_thread->elem, wakeup_less_func, NULL);
	thread_block();

	/* restore interrupt */
	intr_set_level(old_level);

}

>> src/devices/timer.c (line 168)
```
static void timer_interrupt(struct intr_frame *args UNUSED) {
  ticks++;
  thread_tick();

	/* === ADDED === */
	/* iterate sleep_list to check if a thread needs to wake up  */
	struct list_elem *e = list_begin(&sleep_list);

	while (e != list_end(&sleep_list)) {
		struct thread *th = list_entry(e, struct thread, elem);

		/* check if it is not wake-up time yet */
		if (ticks < th->wakeup_tick) {
			break;
		}
		
		/* it is wake-up time */
		e = list_remove(e);
		thread_unblock(th);
	}
	/* ============= */
}
```

#### ALGORITHMS

>A2: Briefly describe what happens in a call to timer_sleep(),
>including the effects of the timer interrupt handler.

When a thread calls `timer_sleep()`, it calculates its wake-up time, disables timer interrupt, puts itself to `sleep_list`, and call `thread_block()` to yield the CPU. \
Everytime the CPU clock ticks, `timer_interrupt()` increments the timer tick count, and checks `sleep_list` if any thread reaches its wake-up time. If it does, `thread_unblock()` is called for that thread to put it into the ready state.

>A3: What steps are taken to minimize the amount of time spent in
>the timer interrupt handler?

If `sleep_list` is not sorted in ascending order of the wake-up time, it takes O(1) to push_back a thread, and O(n) to check all threads when calling `timer_interrupt()`. \
So, we chose to sort the list. It will take O(n) to push_back, but only O(1) for each thread to wake up in `timer_interrupt()`. (It can break the loop immediately if the wake-up time is not reached yet.)

#### SYNCHRONIZATION

>A4: How are race conditions avoided when multiple threads call
>timer_sleep() simultaneously

Pintos is a uniprocessor system, so the multiple threads calling `timer_sleep()` simultaneously is actually interleaved execution. By dealing with race conditions that might occur in `timer_interrupt()` mentioned in A5, the problem is avoided completely.

>A5: How are race conditions avoided when a timer interrupt occurs
>during a call to timer_sleep()?

In `timer_sleep()`, while `sleep_list` is being modified, the list can be corrupted if the timer interrupt occurs and tries to read `sleep_list` during modification. So, we disable the interrupt before modifying `sleep_list` and enable it after that.

#### RATIONALE

>A6: Why did you choose this design?  In what ways is it superior to
>another design you considered?

This design does not waste CPU during its waiting time, and only check the wake-up time for each sleeping thread, while maintaining a sorted list minimized the execution time of the hardware interrupt handler.
