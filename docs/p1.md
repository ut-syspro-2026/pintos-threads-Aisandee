#### ALGORITHMS

>A2: Briefly describe what happens in a call to timer_sleep(),
>including the effects of the timer interrupt handler.

When a thread calls `timer_sleep()`, it calculates its wake-up time, disables timer interrupt, puts itself to `sleep_list`, and call `thread_block()` to yield the CPU. \
Everytime the CPU clock ticks, `timer_interrupt()` increments the timer tick count, and checks `sleep_list` if any thread reaches its wake-up time. If it does, `thread_unblock()` is called for that thread to put it into the ready state.

>A3: What steps are taken to minimize the amount of time spent in
>the timer interrupt handler?

If `sleep_list` is not sorted in ascending order of the wake-up time, it takes O(1) to push_back a thread, and O(n) to check all threads when calling `timer_interrupt()`. \
So, we chose to sort the list. It will take O(n) to push_back, but only O(1) for each thread to wake up in `timer_interrupt()`. (It can break the loop immediately if the wake-up time is not reached yet.)

#### SYNCHRONIZATION

>A4: How are race conditions avoided when multiple threads call
>timer_sleep() simultaneously

Pintos is a uniprocessor system, so the multiple threads calling `timer_sleep()` simultaneously is actually interleaved execution. By dealing with race conditions that might occur in `timer_interrupt()` mentioned in A5, the problem is avoided completely.

>A5: How are race conditions avoided when a timer interrupt occurs
>during a call to timer_sleep()?

In `timer_sleep()`, while `sleep_list` is being modified, the list can be corrupted if the timer interrupt occurs and tries to read `sleep_list` during modification. So, we disable the interrupt before modifying `sleep_list` and enable it after that.

#### RATIONALE

>A6: Why did you choose this design?  In what ways is it superior to
>another design you considered?

This design does not waste CPU during its waiting time, and only check the wake-up time for each sleeping thread, while maintaining a sorted list minimized the execution time of the hardware interrupt handler.

>> src/threads/thread.c (line ..): `thread_donate_priority()` recursively donate priority to the waiting locks.
```
void thread_donate_priority(void) {
  struct thread *cur = thread_current();
  struct lock *lock = cur->lock_waiting;
  int depth = 0;
  enum intr_level old_level = intr_disable();

  /* Loop down the lock chain and donates priority to the lock holders */
  while (lock != NULL && lock->holder != NULL && depth < MAX_NESTED_DEPTH) {
    struct thread *holder = lock->holder;

    /* Donate priority if the lock holder's priority is lower */
    if (holder->priority < cur->priority) {
      
      /* If the holder is in the ready_list, re-insert to keep it sorted */
      if (holder->status == THREAD_READY) {
        list_remove(&holder->elem);
        holder->priority = cur->priority;
        list_insert_ordered(&ready_list, &holder->elem, cmp_thread_priority, NULL);
      } else {
        holder->priority = cur->priority;
      }

    } else {
      /* If holder already has a higher or equal priority, stop donating */
      break; 
    }

    lock = holder->lock_waiting;
    depth++;
  }

  intr_set_level(old_level); 
}
```

3.3 Priority Recalculation & Lock Release

>> src/threads/thread.c (line ..): `thread_recalc_priority()` recalculates the current thread's priority to highest priority of threads waiting for other held locks.
```
void thread_recalc_priority(void) {
  struct thread *cur = thread_current();
  enum intr_level old_level = intr_disable();

  /* reset base priority */
  cur->priority = cur->base_priority;

  /* check all locks held for higher priority waiting threads*/
  if (!list_empty(&cur->locks_held)) {

    for (struct list_elem *e = list_begin(&cur->locks_held); 
        e != list_end(&cur->locks_held);
        e = list_next(e)) {
      struct lock *l = list_entry(e, struct lock, elem);

      if (!list_empty(&l->semaphore.waiters)) {
        /* sort the list to get highest_waiter */
        list_sort(&l->semaphore.waiters, cmp_thread_priority, NULL);

        struct thread *highest_waiter = list_entry(list_front(&l->semaphore.waiters), struct thread, elem);

        if (highest_waiter->priority > cur->priority) {
          cur->priority = highest_waiter->priority;
        }
      }
    }
  }
  
  intr_set_level(old_level); 
}
```

#### ALGORITHMS

>B3: How do you ensure that the highest priority thread waiting for
>a lock, semaphore, or condition variable wakes up first?

Always pick a thread from the front of sorted list. And if there is any modification on thread's priority always compare it with the current highest one on the waiting ready list. In parts that the ordering might be changed, the list was sorted before the front is picked.

>B4: Describe the sequence of events when a call to lock_acquire()
>causes a priority donation.  How is nested donation handled?

If the lock is held, set `lock_waiting` and donate priority to each holder on the chain. Nested donation is limited by `MAX_NESTE_DEPTH`.

>B5: Describe the sequence of events when lock_release() is called
>on a lock that a higher-priority thread is waiting for.

`lock_release()` releases the currently using lock from `locks_held`, resets the thread's priority, recalculates to the highest waiter's (for other held locks) priority to preserve donation from other waiters, clears `lock->holder`, and do `sema_up()`.

#### SYNCHRONIZATION

>B6: Describe a potential race in thread_set_priority() and explain
>how your implementation avoids it.  Can you use a lock to avoid
>this race?

If higher-priority thread wakes up due to time interrupt just after the priority-set thread looking for higher-priority thread on the `ready_list`, the list was already read but the newly woke up thread just being put on it. It can cause race condition.

The implementation involved in the critical section are wrapped in `intr_disable()`/`intr_set_level()`. Since Pintos is uniprocessor, no process can intervene in the middle of disabled timer interrupt.

#### RATIONALE

>B7: Why did you choose this design?  In what ways is it superior to
>another design you considered?

Separating `base_priority` and (active) `priority` makes undoing the donation simple. `locks_held` and `lock_waiting` gives complete and effective information to deal with deadlock when doing and undoing the donation.
